# Agent Atelier

ก่อนเสนอแผน agent ตรวจบริบทและถามข้อมูลที่มีผลสำคัญต่อขอบเขตหรือผลลัพธ์เป็นรอบ พร้อมตัวเลือกและคำแนะนำตามความเหมาะสม เมื่อ brief ชัดแล้วจะสรุปและเสนอแผนโดยไม่ต้องยืนยัน brief แยก ทั้งนี้ยังต้องกดยืนยันแผนก่อนเริ่มงาน

ออฟฟิศ pixel ส่วนตัวสำหรับทีม AI ที่ใช้บัญชี Codex CLI ในเครื่อง รองรับหลายโปรเจกต์ แชต งาน ตารางทำงาน ความทรงจำ และการอนุมัติจากผู้ใช้

## เริ่มใช้งาน

ต้องมี Node.js 24 ขึ้นไป, npm, Git และ Codex CLI ที่ล็อกอินแล้ว (`codex login status`)

```bash
npm install
npm run dev
```

เปิด <http://127.0.0.1:3210> เซิร์ฟเวอร์รับการเชื่อมต่อเฉพาะเครื่องนี้

ใช้งานแบบ production:

```bash
npm run build
npm start
```

หยุดด้วย Ctrl+C งานที่ยังไม่จบจะถูกบันทึกว่า interrupted เพื่อให้ตรวจผลงานก่อนเริ่มใหม่ ปิดแท็บเว็บได้โดยไม่หยุดงาน แต่ต้องเปิดเครื่องและเซิร์ฟเวอร์ไว้สำหรับ schedule

ใน **ตั้งค่าสมาชิก** เปิดหรือปิด **ใช้ Serena MCP** และ **ใช้ ponytail full** ได้แยกกัน ค่ามีผลกับรอบถัดไปในทุก Project และรวมอยู่ใน backup ค่าเริ่มต้นเปิดทั้งคู่ ติดตั้ง Serena ให้คำสั่ง `serena` อยู่ใน PATH ของ Node server แอปเปิดเฉพาะเครื่องมือสำรวจโค้ดของ Serena หากค้นด้วย Serena ไม่ได้ agent จะอ่านไฟล์ที่เกี่ยวข้องโดยตรง

## การใช้งาน

- ในบทสนทนาใหม่ เลือกโหมด **คุย** และเลือก repo ที่อนุญาตให้แก้ก่อนกดส่ง สมาชิกต้องมีสิทธิ์เขียน ระบบสร้าง Git worktree แยกและใช้ worktree เดิมสำหรับข้อความที่เลือก repo เดิม โดยไม่เพิ่ม task ใน Kanban บทสนทนารองรับหลาย repo โดยเลือกหนึ่ง repo ต่อข้อความ และตรวจ diff หรือ merge แยกตาม repo เปิด **ตรวจ diff** จากบทสนทนาเพื่อดูและอนุมัติ merge ฉบับล่าสุด เมื่อ merge แล้วจะเห็นสถานะรวมแล้ว และการแก้ครั้งถัดไปจะเปิด branch ใหม่จาก branch ปลายทางล่าสุดใน worktree เดิมถ้าพื้นที่ทำงานสะอาด ยกเลิกรอบจากหน้าตรวจ diff ได้ โดยเก็บ branch และไฟล์ค้างใน worktree เดิมไว้ดูจากบทสนทนา และสร้าง worktree ใหม่เมื่อแก้รอบถัดไป งานโค้ดแบบมอบหมายตรงที่ยืนยัน repo ในบทสนทนาจะใช้ worktree ร่วมกัน และต้องตรวจรับงานก่อน merge จากบทสนทนา Worktree ของบทสนทนาไม่รวมอยู่ใน backup

- งานโค้ดที่มอบให้สมาชิกคนเดียวแสดง repository ที่เสนอในหน้าตรวจแผน เลือกเฉพาะ repo ที่ต้องแก้และตรวจ path ก่อนยืนยัน ระบบสร้าง worktree และรอ merge เฉพาะรายการที่อนุมัติ หากขอบเขตไม่ชัดสมาชิกจะถามก่อนเสนอแผน งานที่เริ่มแล้วและ schedule ที่อนุมัติก่อนหน้านี้คงขอบเขตเดิม ส่วน schedule ใหม่จดจำ repo และ path ที่อนุมัติไว้

- แชตแสดงกิจกรรมล่าสุดของแต่ละงานในส่วนที่พับได้ (สูงสุด 200 รายการ) โดยเก็บประเภทและผลของเครื่องมือโดยไม่เก็บคำสั่งหรือผลลัพธ์ดิบ ข้อความความคืบหน้าที่สมาชิกทำเครื่องหมายไว้จะแสดงในกิจกรรม ส่วนข้อความที่แยกประเภทไม่ได้ยังแสดงในแชต

- เลือกชุดสี **โทนกลาง / เขียวเดิม** และโหมด **ตามระบบ / สว่าง / มืด** ในหน้าตั้งค่า ค่าเริ่มต้นเป็นโทนกลางตามระบบและจดจำแยกในแต่ละเบราว์เซอร์ ฉากออฟฟิศคงสีเดิม

- Kanban แสดงงานหลักพร้อมจำนวนงานย่อยที่เสร็จและ Failed กรองตามวันที่สร้างของงานหลักในเขตเวลา Asia/Vientiane เปิดงานหลักเพื่อสลับดูงานย่อยจากรายการด้านซ้ายบน Desktop งาน Failed แสดงผู้รับผิดชอบและเวลาที่ล้มเหลว หากเป็นข้อมูลเก่าจะแสดงเวลาอัปเดตล่าสุด

- หน้า **ตั้งค่า** เก็บ Tasks หรือ Chats ของโปรเจกต์ที่เลือกเข้าคลังแยกกัน งานที่ยังมีขั้นตอนค้างหรือมีโค้ดที่ต้องตรวจหรือกู้จะยังอยู่บน Kanban เปิดงานที่เก็บจากลิงก์เดิมหรือนำทั้งชุดกลับจากคลังได้ ประวัติแชตเปิดอ่านแยกตามห้องในคลัง ข้อความที่เก็บแล้วจะไม่อยู่ในบริบทของแชตใหม่

- เปิด diff ในแท็บใหม่จากรายละเอียดงานหรือขั้นตรวจ workflow ดูแบบ unified / split และไฟล์ใหม่ที่ยังไม่ tracked ได้ อนุมัติ merge ในหน้า diff หลังตรวจรับตามเงื่อนไขเดิม

- หน้า Task Detail แสดงสถานะและขั้นตอนถัดไป หลักฐานจากผลงานที่ agent ส่ง และสถานะ merge แยกแต่ละ repo พร้อมทางเปิด diff งานที่ถูกขัดจังหวะให้ตรวจผลงานก่อนสร้างงานใหม่ ระบบไม่เริ่มหรือ merge เอง

  งานโค้ดที่ Failed และมี worktree จะแสดงส่วนกู้โค้ดพร้อมชื่อ task, path และ branch ในรายละเอียดงานและหน้ารวมของงานทีม เปิด diff ของ repo ที่ต้องการ แล้วกด **อนุมัติ merge โค้ดจากงาน Failed** แอปจะ commit งานค้างและ merge กลับ branch ปลายทาง หาก worktree เปลี่ยนหลังเปิด diff ให้ตรวจใหม่ เมื่อรวมแล้ว repo จะแสดงสถานะ **รวมแล้ว** โดย task ยังเป็น Failed และการตรวจรับงานทีมยังแยกจากการกู้โค้ด งานที่ถูกขัดจังหวะกู้โค้ดได้ด้วย รวมถึงขั้นเขียนโค้ดที่เสร็จแล้วใน workflow ที่ถูกขัดจังหวะก่อนตรวจรับ

  หาก `office_submit_result` ปฏิเสธผลงาน สมาชิกแก้และส่งซ้ำได้ในรอบเดิมจนระบบรับหนึ่งครั้ง ให้คัดลอกข้อความเกณฑ์จากแผนตรงตัวและส่งหลักฐานหนึ่งรายการต่อเกณฑ์ หากจบรอบโดยยังไม่ผ่านการตรวจรูปแบบ หน้างานจะแสดงเหตุผลที่ปฏิเสธล่าสุด

  หากจบรอบโดยยังไม่มีผลที่ระบบรับ ระบบเปิดรอบกู้การส่งหนึ่งครั้งจากรายงานเดิมด้วยสิทธิ์อ่านอย่างเดียว ขั้นตรวจที่ยังยืนยันบางรายการไม่ได้และไม่มีผลตรวจที่ไม่ผ่านจะพักในสถานะ **รอตรวจเพิ่ม** เมื่อสภาพแวดล้อมพร้อม กด **ตรวจต่อ** ที่งานเดิมเพื่อใช้หลักฐานเดิมและตรวจรายการที่ค้าง ขั้นปลายน้ำแสดง **รอขั้นก่อนหน้า** และเริ่มได้เมื่อหลักฐานต้นทางพร้อมตามเงื่อนไขการอนุมัติ

  เมื่อขั้นลงมือทำส่งผลไม่ครบ ระบบเก็บเหตุผล สิ่งที่ทำแล้ว สิ่งที่เหลือ และสิ่งที่ต้องการ หาก agent ระบุว่าทำต่อได้เอง ระบบต่อใน worktree เดิมสูงสุดสองรอบต่อขั้น การกด **ทำงานต่อ** เองไม่เติมจำนวนรอบ หากต้องรอผู้ใช้หรือไปต่ออัตโนมัติไม่ได้ ระบบแสดงเหตุผลและทางเลือกในหน้างาน งานที่ถูกขัดจังหวะเมื่อรีสตาร์ตยังต้องตรวจผลงานก่อนเริ่มใหม่

  ถ้าฟังก์ชันหลักพร้อมและเหลือรายละเอียดรองหรือผลตรวจบางส่วน agent ส่งเป็น **พร้อมตรวจรับพร้อมข้อจำกัด** ได้ ผู้ใช้บันทึกผลตรวจเองสำหรับข้อที่ยังไม่ได้ยืนยัน หรือระบุเหตุผลที่ยอมรับข้อยกเว้นรายข้อก่อนส่งต่อ ระบบตรวจฉบับและ diff เก็บผลของ agent แยกจากการตัดสินใจของผู้ใช้ และยังแยกการตรวจรับสุดท้ายออกจากการอนุมัติ merge

- งานทีมใหม่ให้ Boss เสนอ workflow พร้อมผู้ทำ ลำดับ เกณฑ์ตรวจรับ และจุดรออนุมัติ อนุมัติแผนทีมครั้งเดียว แต่แบบต้องกดอนุมัติฉบับล่าสุดแยกก่อน dev เริ่ม ตรวจรับงานก่อนอนุมัติ merge แยกแต่ละ repo และยืนยันปิดงานหลัง merge ครบ งานทั่วไปที่ไม่มีโค้ดปิดหลังตรวจรับได้ งานเดิมยังใช้ flow เดิม

  ขั้นสรุปของ Boss แสดงลิงก์ไฟล์จาก revision ต้นทาง แยกผลตรวจของทีมจากผลที่ผู้ใช้ตรวจยืนยันหรือยอมรับความเสี่ยง และรายงานสถานะ merge ราย repo ตามที่แอปบันทึก เกณฑ์สรุปครบได้แม้ยังมีข้อบกพร่องหรือรายการที่ไม่ได้ตรวจ ผลสรุปและหลักฐานที่เหมือนเดิมจะไม่สร้างข้อความซ้ำในแชต

  เมื่อแก้แผนที่มีแบบอนุมัติแล้ว ต้องเลือกแต่ละแบบว่าจะใช้ผลงานและเกณฑ์เดิมหรือส่งทำแบบใหม่ก่อนยืนยัน การใช้แบบเดิมคงเวอร์ชันและการอนุมัติเดิม ส่วนแบบใหม่ต้องอนุมัติอีกครั้ง ระบบตรวจเวอร์ชันและขั้นที่ต้องรอฝั่งเซิร์ฟเวอร์

- Boss เลือกกระจายงานตามบทบาทและสิทธิ์ โดยใช้สถานะสมาชิก ณ เวลาวางแผนเป็นข้อมูลประกอบ สมาชิกที่กำลังทำงานยังรับงานเข้าคิวได้ แผนใหม่แสดงสถานะและเตือนเมื่อ Boss รับทุกขั้นหรือผู้พัฒนาตรวจงานตัวเอง พร้อมเหตุผลที่ Boss ระบุ คำเตือนไม่ขัดขวางการยืนยันและไม่ได้ตัดสินความเหมาะสม แผนเดิมใช้ปุ่มปรับแผนเพื่อสร้างฉบับใหม่

- งานหลักที่ตรวจรับ workflow แล้วบันทึกเป็นเทมเพลตของ Project ได้ โดยกรอกคำอธิบายและเกณฑ์สำหรับใช้ซ้ำใหม่ในช่องว่าง เทมเพลตไม่เก็บคำสั่ง ผลงาน หรือสถานะเดิม เลือกใช้ เปลี่ยนชื่อ ลบ หรือเปิดงานต้นทางได้จากหน้าสร้างงาน การใช้สร้างเฉพาะ draft พร้อมให้แก้ผู้รับผิดชอบและเกณฑ์ก่อนยืนยันแผน ระบบตรวจสิทธิ์และ repo ปัจจุบันอีกครั้ง หากมีหลายขั้นโค้ดหรือหลาย repo ต้องเลือก repo ให้แต่ละขั้น เทมเพลตอยู่ใน backup และยังใช้ได้เมื่องานต้นทางถูกลบ

  ตรวจ P1 ด้วยข้อมูลชั่วคราว: typecheck, 96 tests และ production build ผ่าน ตรวจใน in-app browser บน desktop 1280×720 โดยบันทึกเทมเพลต โหลดหน้าใหม่ สร้าง draft เปลี่ยนสมาชิกด้วยคีย์บอร์ด เปลี่ยนชื่อและลบเทมเพลต ส่วน mobile 390×844 ตรวจหน้า draft และเปิด Select ด้วยคีย์บอร์ด ไม่พบ console error หรือแนวนอนล้นจอ การ restart และ backup/restore ตรวจด้วย automated tests ไม่ได้เรียก Codex หรือ Google จริง

- เริ่มด้วย Atlas, Nova, Sage และ Pixel ทุกคนแก้ชื่อ บทบาท instructions โมเดล และสีตัวละครได้ ค่าเริ่มต้นอ่านอย่างเดียวและยังไม่มีสิทธิ์ Google
- ในตั้งค่าสมาชิกเลือก reasoning effort ตามระดับที่โมเดลจาก Codex รองรับได้ ค่าเริ่มต้นใช้ค่าของโมเดล งานที่เริ่มแล้วเก็บระดับเดิมไว้ การเปลี่ยนค่ามีผลกับงานใหม่ หากโมเดลไม่รองรับค่าที่บันทึกไว้ ระบบหยุดงานและแจ้งให้เลือกค่าใหม่
- หน้าสร้าง/ตั้งค่าสมาชิกเลือก **ตัวละครเดิม** หรือ **สร้างตัวละคร** ได้ ตัวประกอบ pixel art ทำงานในเครื่อง มีทรงผมสั้น บ๊อบ ยาว และหยิก สีผิว 6 เฉด สีผม สีเสื้อ และแว่น พร้อม preview ใบหน้า/เต็มตัวและปุ่ม **สุ่มตัวละคร** การเปลี่ยนมีผลเมื่อกดบันทึกเท่านั้น ตัวละครเดิมไม่เปลี่ยนเอง
- เริ่มด้วย **General** สำหรับงานทั่วไป มี workspace ถาวรของตัวเอง เพิ่มโปรเจกต์ด้วยชื่อ, path เต็มของ workspace หลัก, description และรายการ repository ที่มีอยู่ เลือกโปรเจกต์ก่อนสร้างงานหรือเปิดแชต
- ข้อความจะถูกตีความก่อน: สนทนาตอบได้เลย ข้อความกำกวมถามเพิ่ม ส่วนงานทุกประเภทสร้าง task ร่างพร้อมแผน กด **ยืนยันและเริ่มงาน** จึงเข้าคิว ทำพร้อมกันสูงสุดสองรอบ โดยสมาชิกคนเดียวไม่ทำสองรอบพร้อมกัน รวมการตีความและการทำงาน
- ถ้าตีความข้อความในแชตส่วนตัวไม่สำเร็จ กด **ลองตีความอีกครั้ง** ใต้ข้อความเดิมเพื่อใช้ข้อความและรูปแนบชุดเดิม หากยังไม่สำเร็จ เลือก **กรอกแผนเอง** เพื่อบันทึกร่างโดยข้ามการตีความ แล้วตรวจแผนก่อนกด **ยืนยันและเริ่มงาน**
- ผลงานใหม่ของ Task หลัก รวมถึงงานที่มาจาก schedule แต่ละรอบ จะอยู่ในคอลัมน์ **รอตรวจรับ** จนผู้ใช้กดตรวจรับจากหน้า Task งานโค้ดอยู่ใน **ตรวจรับแล้ว รอ merge** จนรวมครบทุก repo และยืนยันปิดงาน งานย่อยส่งผลต่อกันตามแผนได้ และ workflow ยังใช้จุดอนุมัติแบบตามเดิม สถานะ Completed ที่บันทึกไว้ก่อนอัปเดตยังใช้ได้
- เปิดรายละเอียดงานเพื่อคุยกับเจ้าของงานในแชตเดิมได้แม้งานเสร็จแล้ว ผลงาน หลักฐานการตรวจ และไฟล์แนบอยู่ในประวัติแชต ส่งคำถามหรือขอแก้จากช่องเดียวกัน เมื่อแก้ในขอบเขตเดิมก่อน merge ระบบใช้พื้นที่ทำงานเดิมและขออนุมัติตามขั้นตอน หลัง merge หรือเมื่อเปลี่ยนขอบเขต ระบบเสนอรอบใหม่ในแชตเดิมเพื่อให้ยืนยันก่อนเริ่ม โค้ดรอบใหม่ใช้ worktree แยกและต้องตรวจรับตามขั้นตอน
- ในแชตของงานที่พักอยู่ พิมพ์ **ทำต่อเลย** หรือ **ลองอีกที** เพื่อใช้แผนและ worktree เดิม ระบบตรวจเงื่อนไขเดียวกับปุ่ม **ทำงานต่อ** และแจ้งขั้นตอนถัดไปหากยังมีคำขออนุมัติหรือผลการดำเนินการภายนอกที่ต้องตรวจ ข้อความที่ส่งขณะเอเจนต์กำลังทำงานจะเข้ารอบนั้นโดยตรง
- แชตแสดงฉบับส่งมอบล่าสุดของแต่ละขั้น เปิดฉบับก่อนหน้าได้จาก **กิจกรรม** สรุปของ Boss แสดงพร้อมลิงก์กลับไปขั้นต้นทางและสถานะ merge ล่าสุดจากแอป ระบบใช้สรุปฉบับที่ส่งครบแล้วซ้ำเมื่อหลักฐานต้นทางยังตรงกัน
- ผลลัพธ์งานและข้อความตอบจากงานมีส่วน **ไฟล์ผลงาน** สำหรับไฟล์ที่ agent อ้างอิงด้วย Markdown link: ดูภาพตัวอย่าง เปิดสเปกข้อความ และดาวน์โหลดไฟล์ เช่น PNG, FigCraft และ Markdown ได้จากพื้นที่ทำงานเดิม ไม่ต้องรวม branch ก่อน
- ห้องทีมใช้ **Boss** ที่ผู้ใช้เลือกหนึ่งคนต่อออฟฟิศในหน้าตั้งค่าสมาชิก เพื่อคุย ตีความ และเสนอแผนกระจายงาน หากยังไม่เลือกจะบันทึกข้อความอย่างเดียว แชตส่วนตัวให้สมาชิกผู้รับตีความเอง การเปลี่ยน Boss ไม่ย้ายงานเดิม
- แชตทุกห้องแนบรูปด้วยปุ่ม **แนบรูป** หรือวาง screenshot จาก clipboard ได้ มี preview และลบก่อนส่ง ส่งเฉพาะรูปได้ รองรับ PNG/JPEG/WebP แบบภาพนิ่ง สูงสุด 4 รูป รูปละ 5 MiB และไม่เกิน 20 ล้านพิกเซล กดรูปในประวัติเพื่อเปิดภาพเต็มในแท็บใหม่
- agent รับรูปจากข้อความต้นทางก่อน แล้วเติมรูปใหม่สุดจากประวัติ 16 ข้อความที่มีสิทธิ์เห็น รวมไม่เกิน 4 รูปต่อ turn จึงถามต่อได้โดยไม่แนบใหม่ถ้ารูปยังอยู่ในบริบท การส่งรูปให้ agent จะส่งผ่านบัญชี Codex เช่นเดียวกับข้อความ; ห้องทีมที่ยังไม่เลือก Boss ยังไม่เรียกโมเดล
- draft ข้อความและรูปแยกตามโปรเจกต์/ห้อง เก็บเฉพาะขณะหน้าแชตเปิดอยู่และคงไว้เมื่อส่งไม่ผ่าน แต่ยังไม่บันทึก draft หลัง reload รูปที่ส่งแล้วเก็บถาวรตามประวัติ ยังไม่มีการลบรูปที่ส่งแล้ว ลากไฟล์มาแนบ หรือรองรับ PDF/HEIC
- agent ปรึกษากันได้เอง แต่การส่งต่องานและการเขียนข้อมูล Google ต้องผ่านหน้า **การอนุมัติ** จำกัดบทสนทนาอัตโนมัติหกรอบก่อนขอให้คุยต่อ
- ดูและแก้ความทรงจำส่วนตัวหรือความรู้ร่วมในหน้า **ความทรงจำ** ระบบส่งเฉพาะข้อมูลของโปรเจกต์ปัจจุบันและความทรงจำส่วนตัวของ agent นั้น
- **จัดห้อง** ใช้ขณะไม่มีงานกำลังทำ ลากเฟอร์นิเจอร์และสมาชิก วางของเพิ่ม หรือลบของที่เลือก แล้วกดบันทึก พื้นที่ทับกันจะไม่ผ่านการบันทึก
- ตารางทำงานรองรับครั้งเดียว รายวัน รายสัปดาห์ และ IANA timezone ค่าเริ่มต้น Asia/Vientiane เมื่อกลับมาเปิดระบบ ตารางที่พลาดจะชดเชยหนึ่งงานและไม่ซ้อนกับงานรอบก่อน หน้าตารางแสดงรอบล่าสุดและรายการที่ต้องดำเนินการของ Project พร้อมลิงก์ Task/การอนุมัติ ข้อมูลรอบเก่าที่ไม่ได้บันทึก Task ID จะแสดงว่าไม่พบ Task แทนการเดา

### Project, repositories และ app prompt

หนึ่ง Project มี workspace หลักสำหรับเอกสารและไฟล์ทั่วไป พร้อม description อธิบายเป้าหมาย ข้อจำกัด และความสัมพันธ์ของระบบ เพิ่มได้สูงสุด 16 repositories แต่ละรายการมีชื่อ, path และ description เช่น frontend Next.js กับ backend Go/Fiber รองรับ path เต็มหรือ relative จาก workspace หลัก โดยบันทึกเป็น canonical absolute path และปฏิเสธ repo ซ้ำ/ซ้อนกัน ระบุ monorepo เพียงครั้งเดียวแล้วอธิบายตำแหน่ง frontend/backend ใน description ได้ Project ที่ไม่มี repo ยังทำงานทั่วไปได้

ช่อง Workspace หลักและ Path ของ repository มีปุ่มไอคอนโฟลเดอร์ด้านขวา พร้อม tooltip **เลือกโฟลเดอร์** บน macOS ปุ่มนี้เปิด native folder chooser บนเครื่องที่รัน server แล้วเติม absolute path เฉพาะช่องที่เลือก กดยกเลิกเพื่อคงค่าเดิม การเลือกเปลี่ยนเฉพาะ draft จนกดบันทึก และยังพิมพ์ path เองได้ทุกระบบ ระหว่างเลือกหรือบันทึก ปุ่มเลือกโฟลเดอร์จะปิดใช้งาน; หากเปิดไม่ได้ จะแจ้งในฟอร์มให้ลองใหม่หรือพิมพ์เอง

Action `path.choose` ผ่าน `POST /api/action` เดิม คืน `result: { path: string | null }` โดย null หมายถึงยกเลิก ใช้ `/usr/bin/osascript` กับ script คงที่ตาม [Apple folder-selection documentation](https://developer.apple.com/library/archive/documentation/LanguagesUtilities/Conceptual/MacAutomationScriptingGuide/PromptforaFileorFolder.html) ไม่รับ script หรือ path จาก request, เปิดได้ครั้งละหนึ่งหน้าต่าง และรอได้สูงสุดประมาณห้านาที ระบบอื่นคืนข้อความให้กรอก path เอง โดยคง Host/Origin และ input limits เดิม

ตรวจ Choose path วันที่ 2026-11-02 ด้วย Node.js 24.22.1: typecheck, 62 tests และ `npm run build -- --webpack` ผ่าน เพิ่ม mock native-process tests สำหรับ Unicode/ช่องว่าง, ยกเลิก, error, output ผิด, lock/retry และระบบที่ไม่รองรับ ตรวจ production ผ่าน in-app browser บน port 3254 ที่ 1280×1024 และ 390×844 ด้วยข้อมูลชั่วคราวและ native process จำลอง: ปุ่มอยู่ขวาของทั้งสองช่อง, Enter/Space, disabled ระหว่างรอ, เติมเฉพาะช่องเป้าหมาย, Cancel คงค่าเดิม, บันทึก/reload, Escape ทิ้ง draft และ error ภายใน dialog ผ่าน ไม่มี horizontal overflow ตรวจ HTTP ปฏิเสธ Host/Origin ภายนอกและ Origin ที่ขาดด้วย 403 ทดลอง launch osascript จริงแล้ว แต่เครื่องมือควบคุม UI เข้าถึงหน้าต่าง native ไม่ได้ จึงยังไม่ได้ยืนยันการเลือก/ยกเลิกในหน้าต่าง macOS จริง ไม่เรียก Codex/Google หรือแตะ `.data/` ของผู้ใช้ ปิด process และ preview ที่สร้างเพื่อทดสอบหลังตรวจ

App prompt อยู่ที่ `prompts/app.md` โหลดครั้งเดียวตอนเริ่ม server และส่งเป็น developer instructions ต่อจากคำสั่งสมาชิก ข้อมูล Project, task, ทีม และ path จริงเติมโดย runtime; description และความทรงจำเป็น reference data ไม่เพิ่มสิทธิ์ ระบบกำชับ agent ให้อ่าน README.md, ปฏิบัติตาม AGENTS.md ใน workspace ของ repo และอ่านไฟล์ที่เกี่ยวข้องตามงาน ไม่โหลดไฟล์ทั้ง project เข้าบริบทเอง แก้ app prompt แล้วต้อง restart server ไม่มีการแทนที่ system policy ของ Codex

งานทั่วไปเก็บไฟล์ใน workspace หลักตามโครงสร้างเดิมหรือตำแหน่งที่ผู้ใช้ระบุ งานโค้ดหนึ่งงานทำ frontend/backend ข้าม repo ได้ โดยสร้าง worktree ทุก repo ที่ผูกกับ Project ภายใต้ `.data/worktrees/<task-id>/<repository-id>` และเริ่มจาก current branch ของแต่ละ repo Agent เริ่มในโฟลเดอร์งานที่รวม worktree และได้รับแผนที่ path ของแต่ละ repo พร้อม description ไม่แก้ repo ต้นฉบับ บทบาทกำหนดความถนัด ส่วน task กำหนดขอบเขตงาน การส่งต่องานยังขอ approval เหมือนเดิม

Project เดิมที่มีเพียง `id/name/path` ใช้ path เดิมเป็น repo แรกโดยไม่ย้ายไฟล์ งาน worktree เดิมยังดู diff/merge ได้ General เดิมที่ยังใช้ชื่อเริ่มต้น “พื้นที่ทำงานส่วนตัว” เปลี่ยนชื่อแสดงเป็น General โดยรักษา path และข้อมูลเดิม ชื่อที่ผู้ใช้ตั้งเองคงเดิม Backup เก็บ description/repo map/สถานะราย repo แต่ restore ตัด path และ branch ที่ใช้รันงานออกตามเดิม ไฟล์ผลงานและ worktree ไม่รวมใน backup

`project.save` รับ `{ id?, name, path, description?, repositories?: { id, name, path, description? }[] }`; หาก client เดิมไม่ส่ง repositories/description การแก้ Project เดิมยังรักษาค่าเหล่านี้ไว้ `GET /api/task-diff?id=<task-id>&repositoryId=<repo-id>`, action `task.merge` และ `git.initialize` รับ `repositoryId` สำหรับงาน/Project หลาย repo ส่วนงานเก่ายังใช้ API เดิมได้

### Preset prompt ตามบทบาท

หน้าสร้าง/ตั้งค่าสมาชิกมี preset 15 บทบาท: Frontend, Backend, Tester, UX/UI Designer, Marketing, DevOps, QA, Customer Support, Server/Linux Security, General Assistant, Planner, Full-stack Developer, Researcher, Content Writer และ Data Analyst เลือก preset เพื่อดูตัวอย่าง Markdown โดยยังไม่เปลี่ยนข้อมูล กด **ใช้ preset** เพื่อแทนที่บทบาทและ prompt ฉบับร่าง หรือ **รีเซ็ต prompt** เพื่อแทนที่เฉพาะ prompt ด้วย preset ที่เลือก จากนั้นแก้ไข Markdown เพิ่มได้ การเปลี่ยนมีผลเมื่อกด **บันทึก** เท่านั้น ปิดหน้าต่างเพื่อทิ้งฉบับร่าง

สมาชิกใหม่เริ่มด้วย General Assistant; office ใหม่ใช้ Planner สำหรับ Atlas, Full-stack Developer สำหรับ Nova, Researcher สำหรับ Sage และ UX/UI Designer สำหรับ Pixel สมาชิกเดิมไม่ถูกเปลี่ยน prompt อัตโนมัติ ระบบจำ preset ที่ใช้แม้ปรับแต่งข้อความ และเก็บทั้ง preset ID กับ Markdown ใน backup เดิมที่ไม่มี preset ID ยังนำเข้าได้ Tester เน้นเขียน tests/ทำ reproduction ส่วน QA เน้น acceptance, regression และความพร้อมก่อน release

ไฟล์ภาษาอังกฤษอยู่ใน `prompts/roles/*.md` มีหัวข้อ Role, Responsibilities, Working Process, Quality Standards, Boundaries และ Deliverables จำกัด 16,000 ตัวอักษร โหลดครั้งเดียวตอนเริ่ม server ผ่าน catalog ที่กำหนดไว้ใน `server/role-presets.ts` และอ่านได้จาก `GET /api/role-presets` เมื่อแก้ไฟล์ให้ restart server แล้วกดรีเซ็ต/บันทึกสมาชิกที่ต้องการ ข้อความที่เคยบันทึกจะไม่เปลี่ยนเอง หากโหลด catalog ไม่สำเร็จจะแสดง error และปุ่มลองใหม่ แต่ยังแก้ไข/บันทึกคำสั่งสมาชิกเดิมได้

Prompt ส่งเป็น developer instructions ภายใต้ข้อกำหนดของ Codex และ safeguards ของ office ไม่ได้เพิ่มสิทธิ์หรือยกเลิกการอนุมัติ

ตรวจฟีเจอร์ preset วันที่ 2026-11-02 ด้วย Node.js 26.3.1: `npm run typecheck`, `npm test` (44 tests) และ `npm run build` ผ่าน ตรวจ 15 ไฟล์/ID/หัวข้อ/ขนาด, ไฟล์หายหรือเนื้อหาผิด, seed ของ office ใหม่, สมาชิกเดิม, prompt ที่ปรับแต่ง, restart, backup round trip และ fake Codex ที่ได้รับ Markdown พร้อม safeguards เดิม

ตรวจ production ผ่าน in-app browser ด้วยข้อมูลชั่วคราวบน port 3242 ที่ 1536×1024 และ 390×844: เลือกโดยไม่ทับ prompt, Apply ด้วย Enter, Reset ด้วย Space, ปรับแต่ง/บันทึก/reload, ปิดโดยไม่บันทึก, default สมาชิกใหม่, สร้าง QA บนมือถือ และเปิด preview ด้วย keyboard ผ่าน ไม่พบ horizontal overflow หรือ framework error overlay และ console ไม่มี warning/error ตรวจ catalog/Host/Origin ผ่าน HTTP และใช้ read-only proxy บน port 3243 จำลอง 503 เพื่อตรวจ error, editor/Save ที่ยังใช้งานได้ และ Retry ที่คง draft ไว้ ไม่ได้ใช้ Codex หรือ Google จริง ไม่แตะ `.data/` ของผู้ใช้ และหยุดเซิร์ฟเวอร์ทดสอบหลังตรวจ

งานที่เริ่มใหม่ใช้ `approvalPolicy: "on-request"` และ `approvalsReviewer: "auto_review"` ให้ Codex ตรวจและอนุมัติคำขอใช้สิทธิ์แทนผู้ใช้ ตาม [Auto-review](https://learn.chatgpt.com/docs/sandboxing/auto-review) โดยคง sandbox ตามสิทธิ์สมาชิกและ consultation แบบอ่านอย่างเดียว งานที่เริ่มแล้วใช้ policy เดิมจนจบ หากระบบตรวจปฏิเสธหรือไม่สามารถอนุมัติได้ จะแสดงเหตุผลในแชตและประวัติคำขอโดยไม่อนุมัติหรือ retry แทนเอง หาก Codex ไม่รองรับหรือบัญชีใช้งานโหมดนี้ไม่ได้ จะแสดงข้อผิดพลาดตามจริง

ใน workflow ที่อนุมัติแล้ว ขั้นลงมือทำและขั้นตรวจสอบอิสระเริ่ม dev server ชั่วคราวเพื่อทดสอบผ่านเบราว์เซอร์ได้โดยไม่ต้องขออนุมัติซ้ำใน Agent Atelier ให้ Dev ใช้ worktree ที่ได้รับมอบหมายและผู้ตรวจใช้สำเนาของผลงานฉบับที่ตรวจ เปิดเฉพาะ loopback (`127.0.0.1` หรือ `::1`) บนพอร์ตว่าง ใช้ซ้ำในรอบทดสอบและหยุดเฉพาะ process ที่ตนเริ่มเมื่อเสร็จ หาก sandbox บล็อก ให้ขออนุมัติคำสั่งผ่าน Codex ตามนโยบายของรอบนั้น หากยังรันไม่ได้ ให้บันทึกคำสั่ง ผลที่พบ และรายการที่ยังไม่ได้ตรวจ แล้วทำ checks ที่เหลือ แยกผล mock ออกจากผล live API

การส่งต่องาน เริ่ม Git รวมโค้ด และเขียน Gmail/Calendar ยังต้องให้คุณอนุมัติ คำขอยาวในหน้าต่างอนุมัติเลื่อนอ่านรายละเอียดเต็มได้ โดยหัวข้อ ปุ่มปิด และปุ่มตัดสินใจอยู่ในจอ รายการและประวัติย่อข้อความเฉพาะการแสดงผล ไม่แก้ข้อมูลเดิม

ตรวจวันที่ 2026-11-02: typecheck, 45 tests และ production build ผ่าน ใช้ fake Codex ตรวจ policy/sandbox ทั้ง read-only และ workspace-write รวม consultation, ผลปฏิเสธ/timeout/ยกเลิกของ Auto-review และการกันอนุมัติซ้ำ ตรวจ production ผ่าน in-app browser บน port 3246 ที่ 1536×1024 และ 390×844 ด้วยคำขอจำลองยาวกว่า 10,000 ตัวอักษรและข้อความไม่เว้นวรรค: ปุ่มอยู่ในจอ อ่านรายการเก่าได้ครบ เลื่อนถึงท้ายด้วย keyboard, Escape ปิด, Enter ปฏิเสธ และ Space อนุมัติผ่าน ไม่พบ horizontal overflow หรือ console warning/error ใช้ข้อมูลชั่วคราวแยกจาก `.data/` และปิดการเรียก Codex จริง ไม่ได้ทดสอบ Auto-review กับบัญชีจริงหรือเขียน Google จริง

### งานโค้ด

ทุก repository ของโปรเจกต์ต้องมี Git repository, initial commit, branch ที่ระบุชื่อได้ และไม่มีไฟล์ที่ยังไม่ commit ก่อนเริ่ม สมาชิกต้องได้รับสิทธิ์ workspace-write งานจะใช้ branch `codex/office-*` กับ worktree ของตัวเองในแต่ละ repo โฟลเดอร์ต้นฉบับจะยังไม่เปลี่ยนจนกดอนุมัติรวมงาน

เปิดรายละเอียดงาน อ่านผลลัพธ์และผลทดสอบจาก agent แล้วเปิด diff ก่อนกดรวมแต่ละ repo ระบบจะ commit การแก้ไขใน worktree และ merge กลับ branch เดิม โดยไม่ push แสดงจำนวน repo ที่รวมแล้วและเก็บ path ต้นทางไว้กับงาน จึงไม่เปลี่ยนปลายทางตามการแก้ตั้งค่า Project ภายหลัง หากเกิด conflict จะ abort การ merge ของ repo นั้นและเก็บ worktree ไว้ให้ตรวจต่อ การรวมหลาย repo ไม่ใช่ transaction เดียว: repo ที่รวมสำเร็จแล้วคงผลนั้นไว้ ส่วน repo ที่เหลือรอการอนุมัติ/แก้ conflict แยกกัน เมื่อบาง repo รวมแล้ว การปรึกษาต่อเป็น read-only; สิทธิ์กลับมาเขียนงานเดิมมีเฉพาะเมื่อทุก repo ยังไม่รวม

หากเตรียม repo ถัดไปไม่สำเร็จ ระบบเก็บ worktree ที่สร้างแล้วไว้กับงานที่ล้มเหลว ไม่เริ่ม Codex และไม่แก้ repo ต้นฉบับ Worktree/branch ยังเก็บหลัง merge เพื่อรักษาลิงก์ไฟล์ผลงาน ไม่มีการลบทิ้งอัตโนมัติ Dependencies และไฟล์ local ที่ Git ไม่ track จะไม่ถูกคัดลอกไป worktree

ปุ่ม **เริ่ม Git…** ของแต่ละ repo ขออนุมัติรัน `git init` ที่ path ที่แสดงเท่านั้น หากเปลี่ยน path ต้องขอใหม่ คุณต้องเลือกไฟล์และทำ initial commit เอง เพื่อไม่ให้แอปนำไฟล์ส่วนตัวหรือ secret ไป track อัตโนมัติ

### Gmail และ Google Calendar

ไปที่ **เชื่อมต่อ** แล้วตั้งค่า Google OAuth Client ประเภท Desktop app จาก Google Cloud project ที่เปิด Gmail API และ Calendar API หาก consent screen อยู่ใน Testing ให้เพิ่มบัญชีคุณเป็น test user จากนั้นกรอก Client ID / Client secret และกดเชื่อมบัญชี การเชื่อม Google แยกจากการล็อกอิน Codex

ขอ scopes สำหรับอ่าน Gmail/ส่งอีเมล และอ่านนัดหมาย/แก้นัดหมายในปฏิทินที่คุณเป็นเจ้าของ เวอร์ชันนี้ใช้ primary calendar จากบัญชี Google หนึ่งบัญชี เปิดสิทธิ์ Google ให้สมาชิกแต่ละคนจากหน้าตั้งค่าสมาชิก

การส่งอีเมลและสร้าง/แก้นัดหมายจะแสดงเนื้อหา ผู้รับ เวลา เขตเวลา และผู้เข้าร่วมให้อนุมัติก่อนเสมอ การอนุมัติซ้ำไม่ส่งคำสั่งซ้ำ หากระบบหยุดหรือเครือข่ายขาดระหว่างส่ง แอปจะแสดงผลว่าไม่แน่ชัดและไม่ retry เอง ให้ตรวจ Gmail/Calendar ก่อนเริ่มใหม่ OAuth token อาจต้องเชื่อมใหม่ตามนโยบาย Google โดยเฉพาะแอปใน Testing

ยังไม่ได้ทดสอบ OAuth และการส่งข้อมูลกับบัญชี Google จริง การทดสอบอัตโนมัติใช้ provider จำลองเพื่อยืนยันขอบเขตการอนุมัติ

### Export / Import office

เปิดหน้า **สำรองข้อมูล** แล้วกด **Export office** เพื่อดาวน์โหลดไฟล์ JSON สูงสุด 100 MiB รวมผังห้อง สมาชิกและรูปลักษณ์ instructions โมเดล สิทธิ์ โปรเจกต์ งาน แชตพร้อมรูป ความทรงจำ ตารางงาน และประวัติการอนุมัติ ต้องไม่มีงาน queued/running/waiting, การ merge หรือการดำเนินการภายนอกค้างอยู่ก่อน export/import กด **หยุดทั้งทีม** เพื่อหยุดงานได้ แต่ต้องรอ external action ที่เริ่มแล้วให้จบก่อน

เลือกไฟล์เพื่อนำเข้า ระบบจะตรวจ version ข้อมูลอ้างอิง ผังห้อง และรูปภาพ แล้วแสดงวันสำรอง จำนวนข้อมูล และ project paths ที่หาไม่พบ กด **ยืนยันแทนที่ office** เพื่อแทนที่ข้อมูลทั้งหมด ไม่มีโหมดรวมข้อมูล ก่อนแทนที่จะสร้างไฟล์สำรองเดิมพร้อมรูปใน `<OFFICE_DATA_DIR>/backups/` (ค่าเริ่มต้น `.data/backups/`) โดยจำกัดสิทธิ์ไฟล์สำหรับเจ้าของเครื่อง หากสำรองหรือการนำเข้าล้มเหลวจะคงข้อมูลเดิมไว้ หน้าจอแสดง path ของไฟล์สำรองหลังสำเร็จ สามารถเลือกไฟล์นั้นเพื่อนำเข้ากลับได้

หลังนำเข้า ทีมจะพักแม้ restart เซิร์ฟเวอร์ งานค้างเปลี่ยนเป็น interrupted ตารางงานทั้งหมดปิด และคำขออนุมัติที่ pending หมดอายุ ผล executing เปลี่ยนเป็น unknown ส่วน unknown เดิมยังคงอยู่ ต้องตรวจบริการปลายทางก่อนทำซ้ำ ตรวจ path ในหน้าโปรเจกต์และสิทธิ์สมาชิกก่อนเปิดทีมและเปิดตารางงานที่ต้องการเอง ไม่มีการรันชดเชยหรือลองงานเดิมซ้ำโดยอัตโนมัติ

ไฟล์สำรองไม่รวมโค้ด โฟลเดอร์โปรเจกต์ Git/worktree, Codex login, Google Client ID/secret หรือ token ข้อมูลเชื่อม Google ของเครื่องปลายทางคงเดิม แต่สิทธิ์ Google ของสมาชิกที่นำเข้าจะปิดไว้ Project paths ยังคงเป็น path ต้นทาง ต้องแก้เองหากย้ายเครื่อง งานโค้ดที่นำเข้าอ่านย้อนหลังได้ แต่ไม่สามารถดู diff หรือ merge จากข้อมูลสำรอง เพราะไม่กู้ Codex session และข้อมูลอ้างอิง worktree/branch ระบบไม่ลบหรือเขียนทับไฟล์โปรเจกต์/worktree เดิม

ไฟล์ JSON ไม่ได้เข้ารหัสและมีข้อความ ความทรงจำ และข้อมูลส่วนตัวที่เคยป้อนให้ทีม รวมถึง secret ที่คุณอาจพิมพ์ไว้เอง ควรเก็บไฟล์ดาวน์โหลดและไฟล์ใน `backups/` อย่างปลอดภัย รูปเก่าที่ไม่มีข้อความอ้างอิงจะถูกเก็บกวาดตามกลไกเดิมเมื่อเริ่มเซิร์ฟเวอร์ใหม่ ส่วนไฟล์สำรองก่อนนำเข้าจะไม่ถูกลบอัตโนมัติ

## โครงสร้างและข้อมูล

Next.js/React เป็น UI; Phaser เป็นฉาก pixel; Node server เปิด Codex App Server ผ่าน stdio JSON-RPC, รับคำสั่ง HTTP และส่ง snapshot ผ่าน SSE; SQLite เก็บข้อมูลถาวร ไม่มีบริการฐานข้อมูลหรือ queue แยก

ข้อมูลในเครื่องอยู่ใต้ `.data/` ซึ่งถูกละเว้นจาก Git: `office.sqlite`, `google-tokens.json`, workspace เริ่มต้น, `attachments/` และ `worktrees/` ไฟล์ข้อมูล/credential ตั้ง permission สำหรับเจ้าของเครื่องเท่านั้น และไม่ส่ง credential เข้า browser snapshot หรือ model context สำรองโฟลเดอร์นี้ขณะหยุดเซิร์ฟเวอร์

ตัวแปรที่รองรับ: `PORT` (3210), `OFFICE_DATA_DIR` (absolute path ของโฟลเดอร์ข้อมูลอื่น), `CODEX_BIN` (ตำแหน่ง Codex หากไม่อยู่ใน PATH) เวอร์ชันนี้เป็น local single-user ไม่เปิดให้เครือข่ายภายนอก

คำสั่ง agent อยู่ภายใต้คำสั่งและ sandbox ของ Codex ใช้โมเดลจาก `model/list` และแสดงข้อผิดพลาดหากบัญชีเรียกโมเดลนั้นไม่ได้ App Server/dynamic tools ยังเป็น integration ที่อาจเปลี่ยนตามเวอร์ชัน Codex

### แนบรูปในแชต — 2026-11-02

งานจริงมีสถานะ `draft` และแผนแสดงเป้าหมาย ขั้นตอน ผลลัพธ์ ผู้รับผิดชอบ และประเภทงาน อ่านแผนได้ในแชตหรือหน้ารายละเอียดงาน ปรับแผนหรือยกเลิกได้ การพิมพ์แก้ในฟอร์มปิดปุ่มยืนยันไว้ก่อน ต้องส่งปรับแผนและตรวจฉบับใหม่ก่อนยืนยัน ปุ่มผูกกับ `planRevision` ฝั่ง server ปฏิเสธแผนเก่า การยืนยันซ้ำ และการยืนยันระหว่างกำลังปรับแผน คำตอบรับ เช่น “โอเค” ไม่เริ่มงาน การสร้างงานจากฟอร์มและการสร้างใหม่จากงานที่หยุดผ่านขั้นตอนเดียวกัน งานโค้ดเตรียมแผนในสิทธิ์อ่านได้ แต่เริ่มจริงต้องมีสิทธิ์แก้ไฟล์และ Git/worktree ตามกติกาเดิม

Boss ใช้ `prompts/boss.md` ที่กำหนดในโค้ด โหลดเมื่อเริ่ม server เหมือน `prompts/app.md` และใช้เฉพาะรอบตีความห้องรวม ส่วน `prompts/intake.md` กำหนดวิธีแยกสนทนา/ถามเพิ่ม/เสนอแผน/รายละเอียดในขอบเขตเดิม แผนของ Boss ระบุทุกงานย่อย ผู้ทำ คำสั่ง ประเภท และผลลัพธ์ให้ผู้ใช้อนุมัติครั้งเดียว งานย่อยเข้าคิวหลังยืนยันเท่านั้น `dependsOn` อ้าง index ของงานก่อนหน้าเพื่อรอผลก่อนเริ่ม รักษาขีดจำกัดสองงาน/หนึ่งงานต่อสมาชิกและสิทธิ์เดิม งานที่พึ่งพางานล้มเหลวจะไม่เริ่ม หากเปลี่ยนผู้ทำหรือเพิ่มขอบเขตภายหลังต้องเสนอขออนุมัติเพิ่ม คำขอกระจายงานระหว่างทำงานต้องแนบแผนที่ตรวจได้ การปรึกษาอ่านอย่างเดียวและงบหกรอบยังคงเดิม

ใช้ **คุยต่อเกี่ยวกับงานนี้** ในแชตเพื่อผูกข้อความกับ task ของผู้รับในห้องและโปรเจกต์เดียวกัน รายละเอียดที่อยู่ในแผนเดิมทำต่อใน task/worktree เดิม หลังรอบที่กำลังทำจบ โดยเก็บผลลัพธ์และลิงก์ไฟล์เดิม ขอบเขตใหม่เป็นร่างอีกงานหนึ่งที่อ้างงานเดิม งานที่รวมโค้ดแล้ว ขัดจังหวะ ล้มเหลว หรือถูกยกเลิกต้องเสนอแผนใหม่ งานรวมของ Boss ให้ติดตามผลแยกตามงานย่อย

แชตในหน้า Task ส่งข้อความถึงเจ้าของงานโดยตรง หากกำลังรันอยู่จะส่งเข้ารอบเดิม งานที่ทำต่อได้ใช้แผนและ worktree เดิม ส่วนงานที่ต้องใช้ปุ่มปรับ workflow เปิดงานที่พักไว้ หรือยืนยันแผนใหม่ จะตอบในโหมดอ่านอย่างเดียวพร้อมบอกขั้นตอนที่ต้องใช้

Schedule เสนอแผนก่อนเปิดใช้ แสดงความถี่ วัน เวลา และ timezone ในหน้าตรวจแผน กดยืนยันแผนทำซ้ำครั้งเดียวต่อขอบเขต แล้วรันตามกำหนดโดยไม่ถามทุกครั้ง การพัก/เปิดตารางเดิมไม่เปลี่ยนแผน แต่แก้ขอบเขตหรือกำหนดเวลาต้องยืนยันใหม่ Gmail/Calendar writes ยังขออนุมัติแต่ละครั้ง เมื่ออัปเดตระบบ งานเดิมที่ยังไม่ยืนยันและเข้าคิวจะกลายเป็นร่างให้เตรียมแผนก่อน ส่วน schedule ที่ยังไม่มีแผนอนุมัติจะพักโดยเก็บข้อมูลเดิม งานที่เริ่มแล้วทำต่อใน process เดิมได้ แต่เมื่อ restart ยังคงเป็น interrupted ตามกติกาเดิม รวมถึงงานย่อยที่ยังไม่เริ่มของ batch ที่ขัดจังหวะ

API เดิม `message.send` / `POST /api/messages` รับ `taskId?` สำหรับคุยต่องาน ส่วน `task.create` คืนร่าง ไม่เริ่มงาน Action ใหม่ `task.plan` รับ `{ id, body }` เพื่อเตรียม/ปรับแผน และ `task.confirm` รับ `{ id, revision }` เพื่ออนุมัติฉบับล่าสุด `agent.save` รับ `boss?: boolean` และเปลี่ยน Boss เดิมใน transaction ตารางอนุมัติและการป้องกัน Host/Origin เดิมยังคงอยู่

Office backup เก็บ Boss แผน revision ความเชื่อมโยงงาน และ schedule แต่ไม่รวม records ของรอบตีความในไฟล์สำรอง เมื่อ restore ล้างรอบเดิม ถอนสิทธิ์รันจากแผนที่นำเข้า และพัก schedule ให้ตรวจใหม่ รูปและประวัติข้อความยังคงอยู่ ไฟล์สำรองรุ่นเก่ายังอ่านได้

ตรวจด้วย Node.js 24.22.1: `npm run typecheck`, `npm test` (72 tests) และ `npm run build -- --webpack` ผ่าน เพิ่ม fake-Codex tests สำหรับสนทนา/ถามเพิ่มโดยไม่สร้าง task, read-only intake/ปฏิเสธ write approvals, แผนเก่า/ยืนยันซ้ำ/แก้แผนแล้วยังต้องถามเพิ่ม, Boss เฉพาะห้องรวม, งานย่อยและ dependencies/งบปรึกษาหกรอบร่วมกัน, followup ใน task เดิม/รักษาลิงก์ไฟล์, schedule/เปลี่ยนขอบเขต/พัก-เปิดเดิม, cancelled draft labels, backup และ restart โดยไม่ replay งานย่อยของ batch ที่ขัดจังหวะ

ตรวจ production ผ่าน in-app browser ที่ `http://127.0.0.1:3256/` ด้วยข้อมูลชั่วคราวและ Codex จำลอง: เลือก Boss, คุยโดยไม่เพิ่ม task, เสนอ/ปรับแผน v1 → v2, ปิดปุ่มยืนยันเมื่อมีข้อความแก้แผน, ยืนยันด้วย Enter/Space, กระจายงานตาม dependencies จนรวมผล, สร้างงานจากฟอร์ม, ยกเลิกร่าง, เปิด schedule หลังตรวจความถี่/เวลา/timezone และ reload state ผ่าน ตรวจ 1280×960 และ 390×844 ไม่มี horizontal overflow หรือ framework overlay และ console ไม่มี app warning/error ตรวจ HTTP Host/Origin/missing-Origin ตอบ 403 ตามเดิม ปิด preview server หลังตรวจ ไม่แตะ `.data/` ของผู้ใช้ ไม่เรียก Codex หรือ Google จริง จึงยังไม่ยืนยันคุณภาพการตีความ/เสนอแผนกับโมเดลจริง

### Workflow ตรวจแบบ → พัฒนา → ตรวจรับ → merge — 2026-11-03

เกณฑ์ผลงานออกแบบระบุสิ่งที่สมาชิกส่งและตรวจได้ ส่วนการอนุมัติจากผู้ใช้ใช้ `reviewRequired` แยกต่างหาก สำหรับงาน Kafepa ของ Sage ที่ติดจากเกณฑ์เดิม เมื่อเปิดเซิร์ฟเวอร์จะกู้สถานะกลับไปรอตรวจแบบ v1 หากไฟล์ทั้งห้าตรงกับ SHA-256 เดิมและขั้นถัดไปยังไม่เคยเริ่ม ขั้นพัฒนาจะเริ่มเมื่อผู้ใช้กดอนุมัติแบบฉบับนั้น

Boss เสนอ `plan.workflow=true` สำหรับงานทีมใหม่ แต่ละ assignment มี `stage` ระบุ `key` ถาวร, `kind` (`design`, `work`, `review`, `summary`), `repositories`, `reviewRequired` และ `criteria` ที่ไม่ซ้ำ แผนแสดงผู้ทำ ขอบเขต เกณฑ์ และ dependencies ก่อนอนุมัติ งานเล็กข้ามขั้นที่ไม่จำเป็นได้ ทุก workflow จบด้วยงาน summary ของ Boss ที่รอทุกขั้น งานโค้ดต้องมี review ตรวจรวมหลัง implementation ครบ และต้องรอ design ทั้งหมด หากมีขั้นออกแบบ ขั้นนั้นต้องรอผู้ใช้กดอนุมัติผลงานล่าสุดก่อนส่งต่อ ไม่ใช้ข้อความตอบรับเป็นการอนุมัติ ผู้ทำ design/work/review ต้องได้รับ workspace-write อยู่ก่อน โดยขั้นทั่วไปเขียนในพื้นที่ผลงานหรือสำเนาสำหรับทดสอบแยกจากต้นทาง ส่วน summary ใช้ read-only เสมอ

ในแชตและรายละเอียดงานมีประวัติผลงานและผลตรวจแต่ละฉบับ กดส่งกลับแก้ได้หลายครั้ง แบบต้องมีภาพ PNG/JPEG/WebP ที่อ่านได้พร้อมสเปก ส่งไฟล์ที่อ้างอิงผ่านกลไก task-file เดิมแล้วเก็บสำเนาและ SHA-256 ต่อเวอร์ชัน ข้อความจากงานผูก `deliveryRevision` จึงไม่เปลี่ยนภาพเก่าเป็นภาพใหม่ การเสนอชื่อไฟล์อย่างเดียวหรือจบ turn โดยไม่ส่งหลักฐานครบไม่ถือว่าสำเร็จ แต่ละขั้นต้องใช้ `office_submit_result` ส่ง output และหลักฐานสำหรับทุก criterion; failed/unverified หยุดการส่งต่อและแสดงข้อที่ติดขัด โดยผู้ใช้ยืนยันรายการ unverified ของขั้นลงมือทำที่เข้าเงื่อนไขได้จากแชต ไม่ถือว่าโมเดลกล่าวว่า passed เป็นการพิสูจน์แทนผลทดสอบจริง ผู้ใช้ยังตรวจแบบและตรวจรับเอง

งานโค้ดเลือก repo จากแผนที่อนุมัติและยึด source path ที่บันทึกไว้ เจ้าของหนึ่งคนต่อ repo ทำต่อใน worktree เดิม คนละ repo ทำพร้อมกันได้ไม่เกินขีดจำกัดสองงานเดิม หากเป็น monorepo ให้ใช้ fullstack คนเดียวพร้อมที่ปรึกษาอ่านอย่างเดียว การแก้หลัง dev เริ่มพักขั้นที่ได้รับผลกระทบ ให้ Boss เสนอแผนแก้ซึ่งผู้ใช้ต้องอนุมัติใหม่ เก็บงานและ worktree เดิมไว้ เปลี่ยนเจ้าของ/ลบ assignment ที่มี worktree แล้วไม่ได้ ต้องแยกเป็นงานใหม่ ขั้นที่ไม่เกี่ยวข้องยังทำต่อได้ แต่เปลี่ยนแผนของขั้นที่กำลังทำต้องพักก่อน

ผู้ตรวจและ Boss ได้แผนที่งานต้นทาง เวอร์ชันแบบ และสำเนา frontend/backend ชุดเดียวกับที่ส่งตรวจใน scratch workspace ไม่ต้อง merge ต้นทางก่อน สำเนาไม่รวม `.git`, `node_modules`, `.next`, `.data`, symlink และไฟล์ข้อมูลลับที่รู้จัก หากต้องเตรียม dependencies/config เพิ่ม ให้ระบุและทำภายใต้สิทธิ์เดิม ห้ามอ้างผลทดสอบที่รันไม่ได้ว่า passed ตรวจว่าไฟล์ต้นฉบับในสำเนาไม่ถูกแก้และโค้ดต้นทางยังตรงกับฉบับส่งตรวจ หากไม่ตรงต้องตรวจใหม่ ผลที่ผ่านครบจึงส่งถึง Boss ให้ตรวจ brief/หลักฐานและเขียนสรุปจริง จากนั้นรอผู้ใช้ตรวจรับ

การตรวจรับผูกกับ fingerprint ของทุกขั้น เมื่อมีโค้ดต้องเปิด diff และอนุมัติ merge แยก repo หลังตรวจรับ ฝั่ง server ตรวจเวอร์ชันและสถานะ workflow อีกครั้งก่อน merge รักษา branch/source identity/clean-tree/conflict abort เดิม ไม่ push และไม่ deploy การ merge บาง repo ไม่ปิดงานหรือย้อนสิ่งที่รวมแล้ว หากมีการแก้หลัง partial merge ให้เสนอเป็นงานใหม่ เมื่อรวมครบ ผู้ใช้กดยืนยันปิดงานและ Boss ส่งสรุปพร้อมสถานะปิดงาน

API เพิ่ม `workflow.decide` ผ่าน `POST /api/action` รับ `{ id, revision, decision, body? }` โดย decision เป็น `approve`, `revise`, `accept`, `replan`, `close` การกดยืนยันซ้ำและฉบับเก่าถูกปฏิเสธ Claim การเปลี่ยน workflow ก่อนรอ I/O `GET /api/task-file` รับ `revision?` สำหรับไฟล์ฉบับเดิม ส่วน `GET /api/task-diff` คืน `version` เพิ่ม ซึ่ง `task.merge` ของขั้น workflow ต้องส่งกลับมาด้วย ข้อจำกัด Host/Origin และการอ่านไฟล์เดิมยังคงอยู่

ปิดแท็บไม่หยุดงาน pending design review/final acceptance คงอยู่หลัง restart ส่วน execution ที่ขัดจังหวะและงานปลายทางไม่ replay อัตโนมัติ ต้องตรวจผลงานและเสนอแผนทำต่อ Office backup เก็บ metadata ของ workflow/เวอร์ชัน/หลักฐาน แต่เหมือนไฟล์ผลงานเดิม ไม่บรรจุไฟล์ snapshot หรือ worktree เมื่อ restore ถอนสิทธิ์รัน การตรวจรับ และ path ที่ใช้ทำงาน พร้อมพัก workflow ให้ตรวจใหม่ ไม่มีการย้ายงานเก่าเข้า workflow โดยอัตโนมัติ

ตรวจด้วย Node.js 24.22.1: typecheck, 83 tests และ production build แบบ Webpack ผ่าน ตรวจ flow ใน in-app browser ด้วย Codex จำลองและ Git repos ชั่วคราว: แก้แบบสามรอบ อนุมัติ v4 ตรวจรับหลัง Boss สรุป ตรวจ diff และ merge ทีละ repo ปิดงานและ reload ได้ ตรวจที่ 1280×960 และ 390×844 ไม่พบ console error หรือ horizontal overflow ตรวจไฟล์ผลงานย้อนหลังและปฏิเสธ Origin ภายนอกแล้ว ยังไม่ได้ทดสอบ login หรือโมเดลจริง

งานที่มอบให้สมาชิกคนเดียวสามารถกด **พักงาน** ในรายละเอียดงานได้ ทั้งงานในคิวและงานที่กำลังทำ เมื่อรอบ Codex จบ ระบบจึงแสดงว่าพักแล้วและให้พิมพ์คำสั่งเพิ่มเติมหรือกด **ทำงานต่อ** เพื่อเข้าคิวเดิม ระบบเก็บคำสั่งเดิม คำสั่งเพิ่มเติม ผลงาน และ worktree ไว้ งานที่พักคงอยู่หลังรีสตาร์ตเซิร์ฟเวอร์ หากผลการเขียน Google ยังไม่ทราบ ให้ตรวจปลายทางและยืนยันก่อนทำต่อ งานทีมใช้การเสนอแผนแก้ตามเดิม

เมื่อขั้นลงมือทำใน workflow ส่งรายงานว่าผลงานยังไม่ครบ ขั้นนั้นขึ้น **ส่งงานยังไม่ครบ · รอคุณตรวจ** และขั้นที่ต้องใช้ผลงานยังรออยู่ เปิดรายละเอียดขั้นเพื่อคุยกับเจ้าของงานแบบอ่านอย่างเดียว แล้วกด **ทำงานต่อ** เพื่อใช้แผนและ worktree เดิมพร้อมบริบทจากแชต การเปลี่ยนขอบเขตต้องให้ Boss เสนอแผนแก้ไข ระบบเก็บรายงานและหลักฐานแต่ละฉบับ รวมถึงกู้สถานะงานเดิมที่เข้าเงื่อนไขนี้เมื่อเปิดเซิร์ฟเวอร์โดยรอให้ผู้ใช้กดทำต่อ

งานที่ล้มเหลว ถูกยกเลิก หรือขัดจังหวะ ลบจากรายการหรือหน้ารายละเอียดได้หลังยืนยัน ระบบเก็บไฟล์และ worktree ในเครื่อง แต่ลิงก์ไฟล์ผ่านงานที่ลบจะใช้ไม่ได้ ประวัติแชตและการอนุมัติยังอยู่ และ schedule ไม่เปลี่ยน ระบบปฏิเสธการลบเมื่อมีงานหรือแผนของตารางที่ยังอ้างอิง รวมถึงการอนุมัติที่รอดำเนินการ กำลังดำเนินการ หรือยังไม่ทราบผล
